# Deploy NEST to Render

The repository is ready for a Render Blueprint deployment. The Blueprint creates a Node web service, a Render PostgreSQL database, a pre-deploy migration step, and a health check at /health.

## Before You Deploy

1. Push this project to a GitHub repository.
2. Confirm that .env is not committed.
3. In Render, choose New, then Blueprint, and select the repository.
4. Enter the three Cloudinary values when Render requests them.
5. Set CORS_ORIGIN to the exact deployed frontend URL, for example https://nest-frontend.example.com.

For multiple frontend origins, use a comma-separated value:

~~~text
https://app.example.com,https://admin.example.com
~~~

## Render Configuration

The included Blueprint uses npm ci --include=dev to build because Sequelize CLI runs migrations. On Render's free tier, pre-deploy commands are unavailable, so the start command runs npm run migrate && npm start. If a migration fails, the new deployment does not start.

Render provides PORT automatically. Do not add a fixed production PORT value.

The database connection is injected as DATABASE_URL from the Render PostgreSQL database. DB_SSL is false because the web service uses Render's internal database connection. If you later point DATABASE_URL at an external managed Postgres database, set DB_SSL to true when that provider requires TLS.

## Required Secrets

Set these only in Render's environment-variable UI, never in Git:

- CORS_ORIGIN
- CLOUDINARY_CLOUD_NAME
- CLOUDINARY_API_KEY
- CLOUDINARY_API_SECRET

JWT_ACCESS_SECRET is generated by the Blueprint. Do not replace it casually after users exist, because that invalidates existing access tokens.

## First Deploy Verification

After deployment, open:

~~~text
https://YOUR_RENDER_SERVICE.onrender.com/health
~~~

Expected response:

~~~json
{
  "status": "success",
  "data": {
    "service": "nest-api",
    "database": "connected"
  }
}
~~~

Then run the local demo-admin seeder only if you need it for a demonstration:

~~~text
npx sequelize-cli db:seed:all
~~~

Do not use the demo password in a real production environment. Create a real administrator with a unique strong password instead.

## Ongoing Deployments

Each push to the configured branch triggers a deployment. The application runs migrations during startup on the free tier. Review every new migration carefully: destructive schema changes need a staged migration plan, not a quick rollback.
